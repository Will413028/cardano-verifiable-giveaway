# Development protocol

This is an implementation default, not frozen protocol v1. The metadata/quicknet/SHA-256 ranking/15-confirmation/NFC defaults will be finalized after the deferred preprod experiments. The runnable demo is not an on-chain giveaway.

## Bundle and canonical commitment

`version: development-2`, `algorithm: sha256-ranking-1`, `drawId`, `entrants`, `rules: { winners }`, and `drand: { chainHash, round }` are the only bundle fields. Labels must be trimmed NFC strings, unique, and free of control characters or lone surrogates. CSV imports use only the `label` column and discard contact columns. Email and phone-shaped labels are rejected. The development limits are 10,000 labels and 200 UTF-16 code units per label. From these, the canonical bundle is at most `BUNDLE_BYTE_LIMIT` = 10,000 × (200 × 3 + 3) + 512 = 6,030,512 bytes: in the worst case every code unit is a BMP character taking three UTF-8 bytes, each label adds two quotes and a comma, and the remaining fields fit in 512 bytes. A downloaded proof may also list every label as a winner and is pretty-printed, so files read by the web page and the CLI are limited to `ARTIFACT_BYTE_LIMIT` = `BUNDLE_BYTE_LIMIT` + 10,000 × 603 + 2 × 10,000 × 8 + 4,096 = 12,224,608 bytes. Both constants live in `packages/protocol/index.ts` and are shared by every reader.

SHA-256 is taken over UTF-8 restricted RFC 8785 canonical JSON: object keys sorted by UTF-16 code units, strings serialized as JSON, arrays preserve order, numbers are nonnegative safe integers. Booleans, null, floating point values and control characters are outside this schema. Ten golden vectors are independently generated and checked by `tools/reference.py`; Node and the browser use `packages/protocol/index.ts`.

## Chain commitment

Development metadata label **20261018** contains `protocol`, `drawId`, `bundleHash`, `chainHash`, and `round`. The number was absent from the [CIP-10 registry](https://github.com/cardano-foundation/CIPs/blob/master/CIP-0010/registry.json) when checked on 2026-10-18 (CIPs commit `befcdb7`); it is not registered, and registration is left to the v1 freeze. `development-1` used 674, which CIP-10 assigns to CIP-20 transaction messages; commitments under 674 are not supported. The browser builds a self-transfer that lists the organizer identity key (below) as its only required signer and sets `invalid_hereafter`, shows its estimated fee, then asks the selected CIP-30 wallet to sign and submit to preprod. Before the wallet is asked, the page re-reads the unsigned CBOR with the verifier's reader and refuses any input, output, body field, metadata, required signer or validity bound other than the planned ones; after signing it refuses a transaction without a valid identity-key witness. It requests no private keys. Mainnet is rejected; preprod UTxOs are checked against the preprod indexer before building.

The verifier reads chain evidence from a Blockfrost-shaped indexer (Dolos MiniBF, Blockfrost RYO; ADR `docs/adr/2026-10-19-self-hosted-dolos-indexer.md`). It reads the commitment from the raw transaction CBOR (`/txs/{hash}/cbor`), never from the indexer's metadata JSON. The blake2b-256 hash of the body bytes, exactly as served, must equal the referenced transaction id, and the blake2b-256 hash of the auxiliary data bytes must equal the body's declared auxiliary data hash (field 7); the metadata is then decoded from those bytes. Both the Conway encodings (tag 258 sets, tag 259 auxiliary data) and the earlier ones (plain arrays, a bare metadata map, no `is_valid`) are accepted. A transaction whose `is_valid` flag is false is not a commitment. The organizer identity key must be listed in `required_signers` (field 14) with a vkey witness whose Ed25519 signature over the transaction id verifies (RFC 8032 strict decoding, `@noble/curves`); inputs' previous transactions are not consulted. The verifier also checks with the indexer that the organizer address was an input (`/txs/{hash}/utxos`, excluding collateral and reference inputs), takes the inclusion block and time from `/txs/{hash}`, reads the tip (`/blocks/latest`) to see whether the block at inclusion height + 14 exists, and then reads that historical block (`/blocks/{height}`) for its time. Both inclusion and that confirmation block must precede the selected round. It does not substitute the verifier's current time for the historical confirmation time. An unavailable or incomplete indexer response, including a transaction whose CBOR it does not serve, fails verification. While the indexer has no record of the transaction (`/txs/{hash}` 404) it is not indexed yet; when it lists the transaction but answers 404 for its CBOR, the CBOR is pending and the transaction may already be on chain. On Dolos 1.6.1 the two never differ: the four transaction reads appear together (measured, `docs/plans/2026-10-18-hardening-and-backend/spike-dolos.md`). `tools/reference.py` recomputes the transaction and auxiliary data hashes of the shared fixtures in `tests/transactions.json` with its own CBOR walker.

### Validity upper bound

The commitment transaction's `invalid_hereafter` (body field 3) must be set, its time must precede the round, and the indexer-reported inclusion time must precede it (ADR `docs/adr/2026-10-18-commitment-validity-upper-bound.md`); otherwise the timing check fails. The ledger refuses a transaction in any slot at or after `invalid_hereafter`, so an indexer misreporting the inclusion time can no longer make a commitment included after the round pass. Slots are converted with the pinned preprod slot clock, not with indexer data: slot 86,400 began at Unix time 1,655,769,600 and every later slot lasts one second (preprod genesis read from a public indexer's `/genesis`: system start 1,654,041,600, Shelley slot length 1 s; Byron ran 4 epochs of 21,600 slots of 20 s; checked against the slot and timestamp a public indexer reported for preprod transaction `3883c2a9…`). A network change to these parameters requires updating the constants, not trusting the indexer. The page sets the bound at the round time minus 15 × 20 s (the 15 confirmations at preprod's expected 20-second block interval), so a transaction still unconfirmed by then could not pass anyway. If the bound passes before the transaction is included, the page reports that it expired and that the draw must be committed again with a later round.

### Uniqueness

Uniqueness is decided per organizer identity, not per address and drawId (ADR `docs/adr/2026-10-18-uniqueness-by-interval-overlap.md`). The identity of the organizer address is its stake credential when the address has a stake part, otherwise its payment credential; only key-hash base and enterprise preprod addresses are accepted. The verifier lists the identity's whole history from the indexer, ordered by block height then position in the block. A payment credential is one list, `/addresses/{addr_vkh}/transactions`. A stake credential is the account's address list, `/accounts/{stake_address}/addresses`, followed by `/addresses/{address}/transactions` for every listed address, merged by transaction hash: one transaction that touches several of the identity's addresses is one transaction (Dolos 1.6.1 has no `/accounts/{stake_address}/transactions`; plan decision PD9). Lists are read with `order=asc`, 100 rows a page; a list ends only with a page of fewer than 100 rows, including `[]`. Any other answer from either stage, including HTTP 400 "pagination scan limit exceeded", a 404 for one address and a 5xx, fails verification: the missing page or address may hold the conflicting commitment. The body only selects the message.

The history is limited to L = `HISTORY_ROW_LIMIT` = 2,900 enumerated rows, the sum over every list (one transaction touching three addresses counts three), counted by the verifier rather than left to the node; more addresses than L fail before any address is read. A history over L fails verification. The value comes from the node rather than from cost: Dolos refuses a page when page × count exceeds its `max_scan_items` (default 3,000), and the end of a list is only known from the first page with fewer than 100 rows, so a list of r rows needs page ⌊r/100⌋ + 1. 2,900 is the largest multiple of 100 for which that page (30) stays within the default, so a node left at the default serves every history the verifier accepts; one row more needs a node with `max_scan_items` raised. A full verification makes 5 requests for the referenced commitment, one per list page, one `/txs/{hash}/metadata` per enumerated transaction (the Blockfrost shape has no batch metadata read) and one CBOR read per transaction carrying this protocol's label: 276 requests for a 265-transaction stake identity on the development chain (measured, `spike-dolos.md`), so about 2,940 at L. Anyone can raise an identity's row count by paying outputs to addresses that pair their own payment key with the organizer's stake key; on preprod parameters one maximum-size transaction (16,322 bytes, 248 outputs of 1 ADA) adds 248 rows for about 0.88 ADA in fees (measured on the development chain, whose fee and size parameters equal preprod's), so about 12 transactions, roughly 10.5 ADA in fees with the 1 ADA outputs still the attacker's, push any identity past L and its draws fail. This weakness is open (plan decision PD10).

Each commitment is open from its inclusion until its round. Two commitments of the same identity whose intervals [inclusion, round) overlap both fail, whatever their drawId or round, and the verdict lists the conflicting commitments (`conflicts`, and the detail of the `Unique commitment` check). Two commitments in the same block always overlap, so simultaneous commitments fail closed without needing intra-block ordering. A commitment included at or after its own round fails the timing check and blocks nothing, so a commitment sent after a completed draw cannot invalidate it; consecutive draws whose intervals do not overlap both pass. If the referenced commitment is missing from the enumerated history, uniqueness fails. The history needs only inclusion evidence: a later commitment still awaiting confirmations is compared by its inclusion time and round, without waiting for its confirmations.

Which transactions count as the identity's commitments: an enumerated transaction whose indexer metadata JSON carries this protocol's label is read as CBOR with the same checks as the referenced commitment, and counts only when it is valid and the identity key (the stake key of a base address, otherwise the payment key) is a required signer with a verifying witness. A third party's address that reuses the organizer's stake part (CIP-19 allows this) therefore cannot create or invalidate a commitment, because it cannot sign with the organizer's key; the same wallet committing from another of its payment addresses is counted, because the stake key signs. Which address an enumerated transaction spends from is not consulted.

Commitments from another wallet cannot be ruled out. A published link is an announcement, not proof that publication occurred before the round.

### What the indexer is still trusted for

The CBOR checks bind the referenced commitment's metadata, identity signature and validity bound to its transaction id; what remains is the indexer's word on what exists and when:

- **Omitting transactions.** The identity's history comes from the indexer's enumeration (the account address list and each address's transactions, or the payment credential's transactions), and its metadata JSON only selects which enumerated transactions are read as CBOR. An indexer that leaves out a conflicting commitment or one of the identity's addresses, or hides a label, makes uniqueness pass. Enumeration completeness is always trusted to the indexer: Mithril certifies that a transaction is included, not that a list is complete. Checking CBOR for every enumerated transaction would not help, since the indexer can leave the transaction out of the list instead, and would multiply requests.
- **Keeping the whole history.** The indexer must be a full archive, and its account address list must include addresses whose funds are already spent (Dolos 1.6.1 lists every address that ever received an output under the stake credential, measured with a fully spent address; Blockfrost RYO reads the same way, the Blockfrost specification does not say). A ledger-only or sliding-history node lists no old commitments, and nothing in the Blockfrost shape tells the verifier which kind it reads (Dolos exposes neither its storage mode nor its earliest block).
- **Misreporting the inclusion block and time.** Block height, inclusion time and the 15th block's time are indexer data. The validity upper bound limits the inclusion time from above with a ledger rule; the start of each uniqueness interval and the confirmation timing are still the indexer's report.
- **Misreporting input addresses.** Whether the organizer address was an input of the referenced commitment is the indexer's report (the CBOR holds only input references). Denying it fails the verification; for enumerated transactions input addresses are not consulted, so lying about them changes nothing beyond what omission already allows.

Choosing the indexer is the available mitigation: the CLI has no default and requires `--indexer <Blockfrost-compatible URL>` (https, or http for a node on the same machine), and the verification page reads a visitor-supplied indexer instead of the project's. Cross-checking two indexers by default remains deferred.

## Randomness and selection

Quicknet chain hash: `52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971`. Genesis: 1692803367 Unix seconds. Period: 3 seconds. Round time = genesis + (round − 1) × period. The public key is pinned in `packages/beacon/index.ts` from the [official quicknet announcement](https://docs.drand.love/blog/2023/10/16/quicknet-is-live/).

Verify the unchained BLS signature over SHA-256 of the round encoded as an unsigned 64-bit big-endian integer, using the short G1 signature and the RFC 9380 `BLS_SIG_BLS12381G1_XMD:SHA-256_SSWU_RO_NUL_` domain. Reject point-at-infinity signatures. Require `randomness = SHA-256(signature bytes)`. The recorded fixture is quicknet round 1,000,000, used only for the demo. Relays are tried sequentially and each response is cryptographically verified against the pinned key.

Seed = SHA-256(randomness bytes || bundle-hash bytes). Each participant's score = SHA-256(seed bytes || UTF-8 label). Sort scores ascending, breaking equal scores by original list index, and take the requested number of distinct labels. The downloaded result (`giveaway-proof-2`) contains exactly `network`, the complete bundle, the commitment reference (`txHash` and `owner`), the beacon and the declared winners; the verifier reads inclusion, confirmation and history for that reference from the chain and recomputes every winner rather than trusting the declaration. Any other field is rejected. The pre-round announcement (`giveaway-pending-2`) contains exactly `network`, the bundle, `txHash` and `owner`.

## Sharing and verdicts

Small announcements and results use URL fragments, with a 12,000-character payload threshold. Larger results can be downloaded and hosted by the organizer; a URL query can pin the complete file's SHA-256 hash. Hosted files require browser CORS access. Public verification may expose public labels; contact information is never included by the importer.

Each check is `pass`, `fail` or `unevaluated`. When chain evidence cannot be read, the commitment hash, timing and unique-commitment checks are `unevaluated` rather than computed from the artifact; when the beacon does not verify, winner recomputation is `unevaluated`. A valid beacon signature for the committed round proves the round has been produced, so the verifier does not consult its local clock.

`PASS` requires every check to pass with preprod evidence from the selected indexer. `DEMO PASS` uses simulated chain evidence and a real recorded drand signature; the demo reference is `SHA-256("giveaway-demo-commitment:" || bundle hash)` with owner `demo-organizer`. This only catches a bundle changed without recomputing the reference: anyone can derive a matching demo reference for any bundle, so demo evidence binds nothing. `FAIL` means at least one check failed or was not evaluated. Demo evidence must never be presented as Cardano evidence.

Verification covers selection from the committed list. It does not establish entrant eligibility, list completeness or prize delivery.
