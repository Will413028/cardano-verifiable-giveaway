# Development protocol

This is an implementation default, not frozen protocol v1. The metadata/quicknet/SHA-256 ranking/15-confirmation/NFC defaults will be finalized after the deferred preprod experiments. The runnable demo is not an on-chain giveaway.

## Bundle and canonical commitment

`version: development-2`, `algorithm: sha256-ranking-1`, `drawId`, `entrants`, `rules: { winners }`, and `drand: { chainHash, round }` are the only bundle fields. Labels must be trimmed NFC strings, unique, and free of control characters or lone surrogates. CSV imports use only the `label` column and discard contact columns. Email and phone-shaped labels are rejected. Email-shaped means exactly what the JavaScript pattern `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` matches over UTF-16 code units (`\s` is JavaScript's whitespace class, which includes U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F, U+3000 and U+FEFF): exactly one `@`, not first; no whitespace anywhere; and after the `@`, a `.` that is neither the first nor the last character. `emailShaped` in `packages/protocol/index.ts` decides it in linear time; the pattern itself backtracks quadratically on `a@` followed by dots (plan step 10b) and is kept only as the oracle of a differential test (`tests/email.test.mjs`). The development limits are 10,000 labels and 200 UTF-16 code units per label. From these, the canonical bundle is at most `BUNDLE_BYTE_LIMIT` = 10,000 × (200 × 3 + 3) + 512 = 6,030,512 bytes: in the worst case every code unit is a BMP character taking three UTF-8 bytes, each label adds two quotes and a comma, and the remaining fields fit in 512 bytes. A downloaded proof may also list every label as a winner and is pretty-printed, so files read by the web page and the CLI are limited to `ARTIFACT_BYTE_LIMIT` = `BUNDLE_BYTE_LIMIT` + 10,000 × 603 + 2 × 10,000 × 8 + 4,096 = 12,224,608 bytes. Both constants live in `packages/protocol/index.ts` and are shared by every reader.

SHA-256 is taken over UTF-8 restricted RFC 8785 canonical JSON: object keys sorted by UTF-16 code units, strings serialized as JSON, arrays preserve order, numbers are nonnegative safe integers. Booleans, null, floating point values and control characters are outside this schema. Ten golden vectors are independently generated and checked by `tools/reference.py`; Node and the browser use `packages/protocol/index.ts`.

## Chain commitment

Development metadata label **20261018** contains `protocol`, `drawId`, `bundleHash`, `chainHash`, and `round`. The number was absent from the [CIP-10 registry](https://github.com/cardano-foundation/CIPs/blob/master/CIP-0010/registry.json) when checked on 2026-10-18 (CIPs commit `befcdb7`); it is not registered, and registration is left to the v1 freeze. `development-1` used 674, which CIP-10 assigns to CIP-20 transaction messages; commitments under 674 are not supported. The browser builds a self-transfer that lists the organizer identity key (below) as its only required signer, sets `invalid_hereafter` and withdraws the whole reward balance of the organizer's stake key (0 ADA when it holds none; the ledger accepts no other amount), shows its estimated fee, then asks the selected CIP-30 wallet to sign and submit to preprod. The organizer address must be a base address: an enterprise address has no stake key and no reward account, and the page refuses it with that reason. Before building, the page reads the stake account (`/accounts/{stake_address}`); when the stake key is not registered or not delegated to a DRep it explains the setup instead of building, because the ledger accepts a withdrawal only from a registered stake key delegated to a DRep (protocol version 10 and later; always-abstain is enough), and registration and delegation in the same transaction as the withdrawal are refused (measured on a real ledger, `docs/plans/2026-10-18-hardening-and-backend/spike-withdrawal.md`). The setup is a separate, earlier transaction the organizer makes in the wallet; this page does not build it. Before the wallet is asked, the page re-reads the unsigned CBOR with the verifier's reader and refuses any input, output, body field, metadata, required signer, withdrawal or validity bound other than the planned ones; after signing it refuses a transaction without a valid identity-key witness. It requests no private keys. Mainnet is rejected; preprod UTxOs are checked against the preprod indexer before building.

The verifier reads chain evidence from a Blockfrost-shaped indexer (Dolos MiniBF, Blockfrost RYO; ADR `docs/adr/2026-10-19-self-hosted-dolos-indexer.md`). It reads the commitment from the raw transaction CBOR (`/txs/{hash}/cbor`), never from the indexer's metadata JSON. The blake2b-256 hash of the body bytes, exactly as served, must equal the referenced transaction id, and the blake2b-256 hash of the auxiliary data bytes must equal the body's declared auxiliary data hash (field 7); the metadata is then decoded from those bytes. Both the Conway encodings (tag 258 sets, tag 259 auxiliary data) and the earlier ones (plain arrays, a bare metadata map, no `is_valid`) are accepted. A transaction whose `is_valid` flag is false is not a commitment. The organizer identity key must be listed in `required_signers` (field 14) with a vkey witness whose Ed25519 signature over the transaction id verifies (RFC 8032 strict decoding, `@noble/curves`); inputs' previous transactions are not consulted. The transaction must also withdraw from the organizer's reward account (withdrawals, field 5), read from the same checked bytes; a commitment without that withdrawal fails, whatever list the indexer puts it in. The verifier also checks with the indexer that the organizer address was an input (`/txs/{hash}/utxos`, excluding collateral and reference inputs), takes the inclusion block and time from `/txs/{hash}`, reads the tip (`/blocks/latest`) to see whether the block at inclusion height + 14 exists, and then reads that historical block (`/blocks/{height}`) for its time. Both inclusion and that confirmation block must precede the selected round. It does not substitute the verifier's current time for the historical confirmation time. An unavailable or incomplete indexer response, including a transaction whose CBOR it does not serve, fails verification. While the indexer has no record of the transaction (`/txs/{hash}` 404) it is not indexed yet; when it lists the transaction but answers 404 for its CBOR, the CBOR is pending and the transaction may already be on chain. On Dolos 1.6.1 the two never differ: the four transaction reads appear together (measured, `docs/plans/2026-10-18-hardening-and-backend/spike-dolos.md`). `tools/reference.py` recomputes the transaction and auxiliary data hashes of the shared fixtures in `tests/transactions.json` with its own CBOR walker.

### Validity upper bound

The commitment transaction's `invalid_hereafter` (body field 3) must be set, its time must precede the round, and the indexer-reported inclusion time must precede it (ADR `docs/adr/2026-10-18-commitment-validity-upper-bound.md`); otherwise the timing check fails. The ledger refuses a transaction in any slot at or after `invalid_hereafter`, so an indexer misreporting the inclusion time can no longer make a commitment included after the round pass. Slots are converted with the pinned preprod slot clock, not with indexer data: slot 86,400 began at Unix time 1,655,769,600 and every later slot lasts one second (preprod genesis read from a public indexer's `/genesis`: system start 1,654,041,600, Shelley slot length 1 s; Byron ran 4 epochs of 21,600 slots of 20 s; checked against the slot and timestamp a public indexer reported for preprod transaction `3883c2a9…`). A network change to these parameters requires updating the constants, not trusting the indexer. The page sets the bound at the round time minus 15 × 20 s (the 15 confirmations at preprod's expected 20-second block interval), so a transaction still unconfirmed by then could not pass anyway. If the bound passes before the transaction is included, the page reports that it expired and that the draw must be committed again with a later round.

### Uniqueness

Uniqueness is decided per organizer identity, not per address and drawId (ADR `docs/adr/2026-10-18-uniqueness-by-interval-overlap.md`). The identity is the stake credential of the organizer's key-hash base preprod address; an enterprise address is refused with the reason (it has no reward account, see below). The identity's history is its reward account's withdrawal list, `/accounts/{stake_address}/withdrawals` (plan decision PD10): every commitment withdraws from that account, and the ledger accepts a withdrawal only with the stake key's witness, so only the organizer can add a row (measured on a real ledger: without the stake witness, with the key only in `required_signers`, or with a forged signature, a third party's withdrawal is refused; `spike-withdrawal.md`). Outputs paid to addresses that pair someone else's payment key with the organizer's stake key (CIP-19 allows them) never appear in this list and cost the verifier nothing. A commitment without the withdrawal is invalid itself, so a candidate an organizer keeps in reserve is either in the list or can never pass.

The list is read with `order=asc`, 100 rows a page, in block order and position within the block (Dolos 1.6.1, measured; rows carry `tx_hash`, `amount`, `tx_slot`, `block_time` and `block_height`, no `tx_index`). Reading stops at the first row whose `block_time` is at or after the referenced commitment's round time: a commitment included then cannot overlap the referenced one (below), and nothing the organizer adds after the draw costs requests or counts toward the limit. A list that shows rows out of ascending order fails, since a row before the round might sit behind the stop; a repeated transaction fails too (a transaction withdraws from one account at most once). Otherwise a list ends only with a page of fewer than 100 rows, including `[]`. Any other answer, including HTTP 400 "pagination scan limit exceeded", a 404 for an unknown account and a 5xx, fails verification: the missing page may hold the conflicting commitment. The body only selects the message. The Blockfrost specification gives this endpoint no `from`/`to` (Dolos accepts them), so the verifier does not use them.

The history read before the round is limited to L = `HISTORY_ROW_LIMIT` = 2,900 rows; more fail verification, and the message says that these rows are the organizer's own commitment history, since only the organizer's stake key can add them. The value comes from the node rather than from cost: Dolos refuses a page when page × count exceeds its `max_scan_items` (default 3,000), and the end of a list is only known from the first page with fewer than 100 rows, so a list of r rows needs page ⌊r/100⌋ + 1. 2,900 is the largest multiple of 100 for which that page (30) stays within the default, so a node left at the default serves every history the verifier accepts. A full verification makes 5 requests for the referenced commitment, one per list page, one `/txs/{hash}/metadata` per row read (the Blockfrost shape has no batch metadata read) and one CBOR read per transaction carrying this protocol's label: 270 requests for 261 rows on the development chain, and 270 again after a third party paid 3,224 outputs to 3,224 addresses carrying the organizer's stake key (measured, `dolos-1.6.1-withdrawal-acceptance-report.json`); about 2,940 at L (inferred). Under the previous enumeration (account address list, then every address; plan decision PD9) the same run's account address list grew to 3,226 addresses, each holding at least one row, so that history would have exceeded L and failed; that let anyone fail an organizer's draws for about 10.5 ADA in fees (inferred, `spike-dolos.md`).

Each commitment is open from its inclusion until its round. Two commitments of the same identity whose intervals [inclusion, round) overlap both fail, whatever their drawId or round, and the verdict lists the conflicting commitments (`conflicts`, and the detail of the `Unique commitment` check). Two commitments in the same block always overlap, so simultaneous commitments fail closed without needing intra-block ordering. A commitment included at or after its own round fails the timing check and blocks nothing, so a commitment sent after a completed draw cannot invalidate it; consecutive draws whose intervals do not overlap both pass. If the referenced commitment is missing from the enumerated history, uniqueness fails. The history needs only inclusion evidence: a later commitment still awaiting confirmations is compared by its inclusion time and round, without waiting for its confirmations.

Which transactions count as the identity's commitments: a listed transaction whose indexer metadata JSON carries this protocol's label is read as CBOR with the same checks as the referenced commitment, and counts only when it is valid and the identity key (the stake key) is a required signer with a verifying witness. A real ledger already refuses a withdrawal without that witness; the check still holds against an indexer, or a development chain, that lists one anyway (the Dolos emulator does not validate withdrawals). The same wallet committing from another of its payment addresses is counted, because it withdraws from the same account and the stake key signs. Which address a listed transaction spends from is not consulted.

Commitments from another wallet cannot be ruled out. A published link is an announcement, not proof that publication occurred before the round.

### What the indexer is still trusted for

The CBOR checks bind the referenced commitment's metadata, identity signature and validity bound to its transaction id; what remains is the indexer's word on what exists and when:

- **Omitting transactions.** The identity's history comes from the indexer's withdrawal list, and its metadata JSON only selects which listed transactions are read as CBOR. An indexer that leaves out a conflicting commitment, places it after a row past the round, or hides a label, makes uniqueness pass. Enumeration completeness is always trusted to the indexer: Mithril certifies that a transaction is included, not that a list is complete. Checking CBOR for every enumerated transaction would not help, since the indexer can leave the transaction out of the list instead, and would multiply requests.
- **Keeping the whole history.** The indexer must be a full archive whose withdrawal list records 0 ADA withdrawals and honours `order=asc` (Dolos 1.6.1 does both, measured; db-sync records withdrawals with `ioShelley` enabled and only for transactions that passed phase 2; Yaci Store 0.12.0 ignores `order` and fails the order check). A ledger-only or sliding-history node lists no old commitments, and nothing in the Blockfrost shape tells the verifier which kind it reads (Dolos exposes neither its storage mode nor its earliest block).
- **Misreporting the inclusion block and time.** Block height, inclusion time and the 15th block's time are indexer data. The validity upper bound limits the inclusion time from above with a ledger rule; the start of each uniqueness interval and the confirmation timing are still the indexer's report.
- **Misreporting input addresses.** Whether the organizer address was an input of the referenced commitment is the indexer's report (the CBOR holds only input references). Denying it fails the verification; for enumerated transactions input addresses are not consulted, so lying about them changes nothing beyond what omission already allows.

Choosing the indexer is the available mitigation: the CLI has no default and requires `--indexer <Blockfrost-compatible URL>` (https, or http for a node on the same machine), and the verification page reads a visitor-supplied indexer instead of the project's. Cross-checking two indexers by default remains deferred.

## Randomness and selection

Quicknet chain hash: `52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971`. Genesis: 1692803367 Unix seconds. Period: 3 seconds. Round time = genesis + (round − 1) × period. The public key is pinned in `packages/beacon/index.ts` from the [official quicknet announcement](https://docs.drand.love/blog/2023/10/16/quicknet-is-live/).

Verify the unchained BLS signature over SHA-256 of the round encoded as an unsigned 64-bit big-endian integer, using the short G1 signature and the RFC 9380 `BLS_SIG_BLS12381G1_XMD:SHA-256_SSWU_RO_NUL_` domain. Reject point-at-infinity signatures. Require `randomness = SHA-256(signature bytes)`. The recorded fixture is quicknet round 1,000,000, used only for the demo. Relays are tried sequentially and each response is cryptographically verified against the pinned key.

Seed = SHA-256(randomness bytes || bundle-hash bytes). Each participant's score = SHA-256(seed bytes || UTF-8 label). Sort scores ascending, breaking equal scores by original list index, and take the requested number of distinct labels. The downloaded result (`giveaway-proof-2`) contains exactly `network`, the complete bundle, the commitment reference (`txHash` and `owner`), the beacon and the declared winners; the verifier reads inclusion, confirmation and history for that reference from the chain and recomputes every winner rather than trusting the declaration. Any other field is rejected. The pre-round announcement (`giveaway-pending-2`) contains exactly `network`, the bundle, `txHash` and `owner`.

## Sharing and verdicts

A draw is downloaded as two files: the canonical bundle bytes (`<drawId>.bundle.json`, the exact bytes whose SHA-256 is the committed bundle hash) and the announcement or proof (`<drawId>.announcement.json`, `<drawId>.proof.json`). Small announcements and results also travel in URL fragments, with a 12,000-character payload threshold.

A verification link is a URL query with `tx` (the commitment transaction hash) and `bundle` (the bundle hash), plus `source` when the bundle bytes are published at an HTTPS URL other than the project backend; the page fetches the bytes from `source` or from the backend's copy (`GET /bundles/{tx}`), refuses them unless their SHA-256 equals `bundle`, and verifies in bundle mode. The same link works before the round (the page reports the wait) and after it. The former link that named a hosted proof file and that file's hash is refused with an explicit error: the proof's hash is on no chain. Hosts other than the backend must allow browser CORS access. Public verification may expose public labels; contact information is never included by the importer.

Bundle mode (the link, and `node apps/verifier-cli/index.mjs <bundle.json> --tx <txHash> --indexer <url>`) needs only the bundle and the transaction hash. The demo reference is recognised by its derivation from the bundle hash (above). Any other reference is a preprod transaction whose owner is read from the chain: the spent input address (collateral and reference inputs excluded) whose stake key is a required signer with a verifying witness and whose reward account the transaction withdraws from — the conditions the verifier checks for a named owner. A transaction whose inputs carry more than one such identity is refused as ambiguous, and one with none is not a commitment. Before the round there is nothing to verify; after it the beacon is fetched from the drand relays (the recorded fixture for its own round) and verified, the winners are recomputed and the assembled proof is verified exactly as a downloaded proof. Deriving the owner adds three indexer reads (`/txs/{hash}`, its CBOR and its UTxOs).

The project backend hosts bundle bytes only for a commitment on chain (plan step 10; ADR `docs/adr/2026-10-18-wallet-auth-and-bounded-retention.md`, Amendment 2). An upload (`PUT /bundles/{tx}`) must not exceed `BUNDLE_BYTE_LIMIT`, must be exactly the canonical serialization of what it parses to (so duplicate keys, whitespace, key order or a byte order mark are refused: otherwise a duplicate key could carry arbitrary content past `validateBundle`), must pass `validateBundle`, and must match that transaction's commitment by the verifier's own check (`matchesCommitment`: its SHA-256, drawId and drand round equal the commitment's), read by the backend from its own indexer with the verifier's reads (owner derivation as above, then the commitment with its 15 confirmations). Hosting, deleting and extending are owner operations (plan step 11; ADR Amendments 5 and 6): each request carries its own CIP-30 `signData` signature in `Authorization: CIP30 <COSE_Sign1> <COSE_Key>`, made by the organizer identity's stake key for its reward address over the owner operation text (`ownerOperationText` in `packages/protocol`: the page's domain, the operation, `preprod`, the transaction and bundle hashes, a nonce from `GET /nonce` and a 5-minute window from its issue time), and the key must be the one of the owner read from the commitment transaction; the backend accepts only nonces it issued, at their recorded issue time, each once. Retention is counted from the base time = min(that round's time, the first time this commitment was hosted) (ADR Amendment 5), so a draw whose round lies far ahead is hosted 12 months from its first hosting, not until 12 months after the round; the first hosting time outlives expiry, deletion and takedown until 12 months after the round, so uploading again never starts a new period (an upload past that expiry is refused with 410). Since only the owner's signed upload creates a record, the first hosting time is the owner's: nobody else can start the clock early. Hosting records are keyed by transaction, so anyone committing the same bundle hash in their own transaction gets their own record and cannot take over or remove another's; the bytes are stored once per bundle hash and deleted with the last record naming them (a deletion claims the hash in the database while no record names it, an upload re-checks its record after writing the bytes, and the hourly Cron run reclaims bytes no record names, so concurrent requests or a failed delete neither leave removed bytes behind nor delete bytes a record names). An operator takedown removes every record of the bytes and keeps a tombstone that refuses them from then on. A record expires 12 calendar months (UTC) after its base time: reads refuse it from then, and an hourly Cron sweep deletes it. The owner may extend a live hosting by 12 months at a time, up to 36 months after the base time; the count is kept with the first hosting time, so a deletion and a new hosting keep it. The owner may delete the hosting at any time (the bytes go with the last record naming them). The backend's write routes are rate limited per client address. Each organizer identity may keep 20 bundles hosted. Hosting is a convenience: verification never depends on it.

Each check is `pass`, `fail` or `unevaluated`. When chain evidence cannot be read, the commitment hash, timing and unique-commitment checks are `unevaluated` rather than computed from the artifact; when the beacon does not verify, winner recomputation is `unevaluated`. A valid beacon signature for the committed round proves the round has been produced, so the verifier does not consult its local clock.

`PASS` requires every check to pass with preprod evidence from the selected indexer. `DEMO PASS` uses simulated chain evidence and a real recorded drand signature; the demo reference is `SHA-256("giveaway-demo-commitment:" || bundle hash)` with owner `demo-organizer`. This only catches a bundle changed without recomputing the reference: anyone can derive a matching demo reference for any bundle, so demo evidence binds nothing. `FAIL` means at least one check failed or was not evaluated. Demo evidence must never be presented as Cardano evidence.

Verification covers selection from the committed list. It does not establish entrant eligibility, list completeness or prize delivery.
